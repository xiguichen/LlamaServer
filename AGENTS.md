## Build & test (CI only)

No local Xcode required. Everything runs in GitHub Actions:

1. Commit and push to `main`/`master` (or open a PR).
2. CI pipeline `.github/workflows/build.yml` on an `xcode-27` runner (macOS 27 arm64, Xcode 27 → iOS 27 SDK) runs two jobs:
   - **test**: `xcodegen generate` → `xcodebuild test` (simulator, unit tests only; destination `iPhone 17` — Xcode 27 images have no iPhone 16 device type)
   - **build**: `xcodegen generate` → `xcodebuild` (unsigned Release) → `bash scripts/package-ipa.sh` → upload artifact.
3. Check the "Actions" tab for results. The test job must pass; the build job produces `LlamaServer-unsigned.ipa`.

## CI notes

- `vendor/llama.xcframework` is cached across runs by the release tag + script hash. Only re-downloaded when the tag or `fetch-llama-xcframework.sh` changes.
- **No Package.swift.** Project is defined in `project.yml` (XcodeGen). Always edit `project.yml`, never the `.xcodeproj` directly.
- **No local llama.cpp compilation.** `vendor/llama.xcframework` is prebuilt, fetched with `bash scripts/fetch-llama-xcframework.sh`. Pinned to tag `b11557`.
- The `.xcodeproj` is **never committed** (`*.xcodeproj` in `.gitignore`). CI regenerates it on every run.

## Debugging a deployed build

The app runs on device, so behaviour is diagnosed from its logs — there is no debugger attached and no local build to fall back on.

- **Identify the build before concluding anything.** Every build reports itself: `system_fingerprint` on any chat/completions response is `llamaserver-<sha>`, and the model-load line says `Model loaded (context …, build llamaserver-<sha>)` (`LlamaServerBuildSHA`, injected by CI). A stale artifact and the current one are otherwise indistinguishable — this cost two redeploys on 2026-10-17.
- **Pull the logs off the device over HTTP** (no cable, no Files app): `curl 'http://<device>:8443/logs?name=inference&tail=500'`. Full query (`name`, `tail`, `backups`, `format`) and the payload-file caveat are in the `GET /logs` gotcha below.
- **The in-app panel is not the log.** It renders basic (error/warn/info) lines only, capped and truncated (`LogPanelSpec`); the three on-disk files are authoritative.
- **Prompt/response payloads are opt-in**: they land in the payloads file only while "log prompt & response content" is enabled (which needs log level *Verbose*). Missing prompts are a toggle, not a bug.
- **On-device compliance** is the `llm-compliance-test` skill (runs `llm-comply openai-chat` against a deployed build).
- **Deploying a new build is a LAN push, not a cable**: `scripts/upload-ipa.sh --url http://<device>:8443` downloads the latest green `build.yml` artifact with `gh` and `PUT`s it to `GET|PUT /v1/updates[/ipa?build=<sha>]`; the app stores it in `Documents/updates/` (`LlamaServer-unsigned.ipa`, rotated `LlamaServer-unsigned.prev.ipa`, `latest.json`), the user taps the `.ipa` in Files, and AltStore installs it in place (models survive). Runbook: the `upload-ipa` skill. Three things to hold onto: the build id lives in `latest.json`/the log and **not** in the file name (Files sorts by name, so a hash-suffixed name hides the newest build); the routes exist **only while a model is loaded** (they ride the inference listener — no second port, no second permission prompt), so a build that cannot start a model cannot be replaced this way, and the escape hatch is picking a smaller model in the UI; and validation (`UpdateSpec.rejection`) runs before any filesystem call, so a refused upload — no `?build=`, over the 128 MB cap, no zip header — leaves both slots untouched. The cap is best-effort (Telegraph buffers the whole body before the handler runs; the real IPA is ~4 MB), and uploads are serialized by their own lock, never the inference queue.

## Performance

**Measured, not inferred — [`docs/PERFORMANCE.md`](docs/PERFORMANCE.md) is the baseline** (rig, method, per-phase numbers, and the claims the logs disprove). Read it before making or repeating any performance claim; add a row when you measure something new.

Headline numbers (A19 Pro, 4B Q4_K_M, ctx 131072, KV q8_0, MTP depth 1, build `470957a`):

- **Prompt: 170–350 t/s** for genuinely new tokens. A cold 24k-token agent prompt costs ~80 s; prefix reuse is what makes turns cheap (`decoding 113 new` of 48,450), including across a context recreate.
- **Generation: 10–17 t/s**, falling with context.
- **`verify-gpu` is 80–90% of every MTP round** (51 ms/round at 0.4k context → 149 ms at 47k): the verify pass attends over the whole KV (843 MB at 48k) plus the weights. CPU/host work is ~3 ms/round — micro-optimising the Swift loop cannot move the needle.
- **MTP depth 1 is a measured net win on generation, a loss on prefill** (paired A/B, byte-identical output): **+11–16% generation** at 0.04k–17.7k context, and **~4% slower prefill** in the thermal-bracket run (the first pair, taken straight off a long session, measured +6–11% / −9% — see `docs/PERFORMANCE.md` for both). The prefill cost is the MTP path also mirroring each prompt chunk into the draft context. For a pi-style turn (small delta prefill + a few hundred generated tokens at ~35k) the two roughly cancel.
- **Snapshot round-trip ~1.2 s and ~700 MB of writes per turn** (see the snapshot gotcha below).
- Thermals swing results ~30% (same 48k context: 148.81 vs 103.49 ms/round) — always quote context length, and pair A/B runs.

## Architecture

- **Single process.** llama.cpp linked as a framework (`import llama`), runs in-process. No separate server binary.
- **HTTP server**: Telegraph framework. Intercepts streaming requests via `interceptHandler` on `StreamableServer` (bypasses normal route handler for SSE writes direct to `HTTPConnection`).
- **Serial inference queue**: `DispatchQueue(label: "llama.inference.serial")` — all `LlamaInference` calls go through this queue (not thread-safe).
- **Context recreated** every 10 generations (`contextRecreateThreshold`) to flush Metal GPU/allocator state that can cause hangs. The recreate runs OFF the response path (`RecreateTracker`, called after the finish chunk in streaming), and the prompt-prefix reuse snapshot survives it (`ReuseSurvival`) — a dense model's `cachedTokenIds` and the on-disk seq blob are preserved so the next turn restores from disk instead of re-decoding the whole prompt.
- **Non-streaming** chat completions: synchronous on the serial queue, returns full response once done.
- **Streaming** chat completions: async on the serial queue, each token flushed as SSE via direct connection write. Keep-alive sends empty delta chunks every 2s.

## Important gotchas

- **MTP (Multi-Token Prediction)**: When enabled, `n_outputs_max` (output slots) is resolved by `MtpSpec.resolveOutputSlots` — the larger of the model's GGUF-derived head count (`nextn_predict_layers`, or fallback `n_predict_layers`, `+1` for the main head, fallback 3 when absent, overridable by an explicit count) and the verify batch `maxDraft + 1`. **Must not sample from more slots than the model supports** — will `ggml_abort` in `llama_sampler_sample`. The runtime guard `llama_get_logits_ith(ctx, i) != nil` prevents this (the plain path probes via `MtpProbe`). **A non-negative index is a BATCH token index, not an output slot**: a row with `logits = 0` returns NULL and `llama_sampler_sample` aborts. Read the draft context's logits with index `-1` (last output row), never a batch index whose row has no logits. The target's unmasked nextn hidden states are indexed by token offset within the last `llama_decode` batch, so after the prompt the last token's h is row `lastChunkCount − 1`.
- **MTP speculative depth** is `mtpMaxDraft = 1` (hard-coded, no UI toggle). The round machinery is depth-N capable (chained drafts, N-row verify, draft seed rows), but depth-2 measured **~9–13% slower** on device. Depth 1 is a measured net win on *generation*, not on prefill: a paired A/B (same prompts, temperature 0, byte-identical output, 2026-10-18) measured **+6–11% generation at 9k–35k context** but **~9% slower prefill** on the first pair, and **+11–16% / −4%** in the thermal-bracket re-run (the first pair was taken straight off a long session) — the MTP path also mirrors every prompt chunk into the draft context, and the win is the 2-row verify sharing one weight read (acceptance flat at 2.03 tokens/round). See `docs/PERFORMANCE.md`. Each round drafts up to `mtpMaxDraft` tokens with the `draft` context (`LLAMA_CONTEXT_TYPE_MTP`); the draft token is a greedy `MtpSpec.argmax` (vDSP) over `llama_get_logits_ith(dft, -1)`. The confidence gate (`MtpSpec.draftConfidence >= MtpSpec.pMin`) is off: `pMin` is 0.0 (`MtpSpec.gateEnabled` false), so a computed draft is always verified. The `target` verifies `[idLast] + drafts` in one batch and **every emitted token is sampled from the target**, so a bad draft costs a round but never corrupts output. Verify rows are sampled lazily: sampling stops at the first real that misses its draft or is eog, because later rows are never emitted. `MtpSpeculator.decide` is the pure acceptance rule (`accepted`, `emitCount`, `rollbackPos`, `carryHFromRow = emitCount − 1`). On a full accept the draft context has a one-position gap (the last accepted token was never drafted into it); `MtpSpeculator.draftSeedIndices` lists the missing rows, which are decoded as leading seed rows of the NEXT round's draft decode (one weight pass), not as a separate catch-up decode. Partial accepts stay contiguous after the two-context `seq_rm` rollback. **The draft context must also see the prompt**: llama.cpp drops `ctx_other` for non-Gemma4 archs, so the draft has its own memory, and `mirrorPromptChunkIntoDraft` decodes every target prompt chunk into it (row k = token x_k with target h_{k-1}, logits off), like upstream draft-mtp `process()`. It is skipped when the draft shares the target's memory (`is_mem_shared`). The draft KV is kept across generations and trimmed to the target's reused prefix when `draftPromptTokens` shows it holds the same tokens; otherwise it starts empty. A failed mirror leaves the draft empty, never with a position gap, because a gap makes every later draft decode fail. `llama_sampler_sample` accepts the token it returns, so the driver never calls `llama_sampler_accept` itself. The `MTP stats:` log line reports `accepted`/`depth` (avg accepted drafts per round) plus per-phase timings in ms per round (`MtpPhaseStats`): `draft + verify + sample (N rounds); draft-gpu + verify-gpu + emit + host = wall`. Keep the part before `;` unchanged (log parsers match it); new fields go after it. Metal decode is async and the first logits read waits for it, so the round calls `llama_synchronize` on the draft right after `decodeDraft` and on the target right after `decodeVerify` (free, the read would wait anyway): `draft`/`verify` are CPU enqueue only, `draft-gpu`/`verify-gpu` are the GPU waits, `sample` is CPU sampling only, and `host` is the rest of the wall clock. Logs from before this split bill both GPU waits to `sample`. The plain path logs `plain stats: emitted=N; gpu-wait + sample + host = wall (N steps)` (`PlainStepStats`), syncing the previous decode at the top of each step.
- **Gen clock**: `generate` calls `llama_synchronize` on the target (and on the draft when the prompt was mirrored) right before `prefillEnd`, and the gen clock (`firstTokenTime`) starts there for BOTH paths. Do not move it back into a path: the prompt's GPU tail then lands in plain `gen` but not MTP `gen`, and the MTP/plain ratio stops being comparable. The `generated N tokens` line prints seconds and t/s with 2 decimals, and its `prefill` segment comes from `PrefillStats.segment` — the rate is over the **decoded** tokens (`X of Y, Z reused`), never the full prompt length. Before 2026-10-18 it divided the full prompt by the delta decode time and printed rates like `33116.58t/s` after cache reuse; any log from an older build must be re-derived by hand.
- **Greedy fast path**: when the chain is pure greedy (`MtpSpec.isPureGreedy`: temperature <= 0 and no penalty sampler; the chain and the check share one `MtpSpec.hasPenalties` result), `sampleTarget` takes `MtpSpec.argmax` over `llama_get_logits_ith` instead of `llama_sampler_sample`, which gives the same token (first max on a tie, greedy `accept` is a no-op). It applies to the plain step and the MTP first/fallback/verify rows. On the greedy path only, a NULL logits row yields -1 (`sampler_error`) instead of a sample; the sampler path keeps llama.cpp's behaviour. Any stateful sampler stage (penalties) keeps the sampler path.
- **`llama_memory_clear(mem, false)`** everywhere: `true` also memsets the buffers (~39 ms per call for a 2 GiB q8_0 KV on device). Cleared KV cells are masked, and fresh recurrent cells are zeroed in-graph (`rs_z`), so stale bytes are never read. Decode-failure recovery recreates the context and does not rely on a clear.
- **Plain path token limit**: the loop breaks before decoding the token that reaches the limit (nobody reads its logits), so `decodedGenerated` lags by that token and `cachedTokenIds` excludes it, the same rule as a stop-string break.
- **Metal pre-warm** is gated on the context size (`KVCacheSpec.needsMetalPrewarm(contextSize:)`, >= 32k), never on the micro-batch (only 512/1024). Load logs show `metal pre-warm done` for those contexts.
- **`recreateContext()`** frees old context before creating new one. Sets `contextValid = false` immediately after free so a subsequent failure can't use the dangling pointer.
- **Decode-failure recovery is automatic, and invisible when it can be.** A `llama_decode` failure (`ret = -3`) comes from the GPU discarding our Metal command buffers (`kIOGPUCommandBufferCallbackErrorInnocentVictim` — a GPU reset caused outside this process; llama.cpp then says "recreate the backend to recover"). `recoverFromDecodeFailure()` rebuilds the context and dumps the tail of llama.cpp's own log (`NativeLogRing`, last 16 lines) at error level, because those native lines are routed at `.debug` and are otherwise absent from a default-level device log — without the dump a device log shows only the return code. `generate` is a thin retry wrapper around `generateOnce`: `DecodeRetry` allows one retry only when the failure is `.decode` and nothing was delivered yet (a delivered token cannot be unsent), so a transient GPU fault no longer costs the client a turn. A prompt larger than the context throws `.contextTooFull` (400), never `.decode`.
- **`unload()`** must be called before discarding `LlamaInference` — otherwise ARC runs `deinit` and the (multi-GB) Metal/CPU allocation stays resident, causing next `llama_model_load_from_file` to return NULL (OOM).
- **LLAMA_TAG** in `scripts/fetch-llama-xcframework.sh` must point to a llama.cpp release that publishes an `xcframework.zip` asset. Changing it may require adapting `Sources/App/LlamaInference.swift` for API drift.
- **Stop field** in API: OpenAI sends `stop` as string or array of strings — decoded via `StopField` enum (handles both).
- **Prompt rendering: the model's own GGUF template renders; our fallback only backstops it.** `LlamaInference.formatPrompt` asks the vendored `llama_chat_apply_template` first, and for this model (`qwen35`) it **succeeds on device** — verified 2026-10-17 from a device log: `chat template loaded (7992 chars), tool format=qwenXML`, and not one `chat template: … failed …` line on any request. (The template's `multi_step_tool` scan iterates `messages[::-1]`, which the bundled `minja` cannot do, but that branch only runs when a `tools` list is passed to the template — something this C API cannot do — so in practice it never declines. A jinja2 render done *with* tools shows the thinking scaffold; the device's template render does not.) What it produces is the plain ChatML layout `fallbackPrompt` would also produce (matching the logged `FULL PROMPT`), so the fallback is a backstop for another model or a future API change and must stay byte-compatible with that render: `<|im_start|>role\n{promptText}<|im_end|>\n` per message plus a bare `<|im_start|>assistant\n` primer. Two details are load-bearing: (a) `|trim` applies to the message content **before** the call envelope is appended — `ChatMessage.promptText(format:)` trims the prose first, else pi's replayed prose (which ends `\n\n`) put four newlines in front of `<tool_call>` instead of two; (b) `<tool_response>` user turns are rewritten by `ToolPrompt.normalizeToolResults` (the template's `tool`-role branch is what we emulate). `formatPrompt` logs which renderer ran (`chat template: llama_chat_apply_template failed …` / `chat template: model has no GGUF template …`) — if those lines appear the fallback is live and the prompt shape has changed; treat that as a signal, not noise.
- **Tool calls** are implemented via system prompt injection (`ToolPrompt.inject`, a pure tested builder in `ToolPrompt.swift`), not GBNF grammar. `ToolWireFormat.detect(template:)` reads the model's GGUF chat template (`LlamaInference.chatTemplateString`, set at load) and picks the **model's own** wire format: a Qwen3.5 template (which carries `<function=…>`/`<parameter=…>` literally) gets `qwenXML` — schemas in a `# Tools … <tools>{json}</tools>` system block and calls as `<tool_call>\n<function=NAME>\n<parameter=K>\nV\n</parameter>\n</function>\n</tool_call>`; anything else falls back to the `jsonHermes` envelope `<tool_call>{"name":…,"arguments":{…}}</tool_call>`. This matters: injecting the JSON format to a Qwen3.5 model puts it out of distribution and it answers with prose instead of a call (verified on device — the native format calls deterministically). The vendored C API (`llama_chat_apply_template`) has **no `tools` parameter** and the framework exports no `common_chat_*` symbols, so llama.cpp's template-driven rendering is unavailable; we emulate the template's `tools` branch instead. `inject` prepends the block to the leading system message (stable every turn, so KV-prefix reuse is preserved) and, for `qwenXML`, rewrites `role:"tool"` turns into the `<tool_response>` user turn the template produces (`normalizeToolResults`) — the generic template has no tool role. There is **no trailing reminder** any more (the old one was a workaround for the wrong format). `ToolCallParser.parse()` extracts calls from **both** syntaxes (JSON and XML, including an unclosed XML call) post-generation, typing XML parameter values against the tool schema (`parse(_:tools:)`: string-typed params stay strings, everything else is JSON-normalized, matching llama.cpp's schema-aware Qwen parser in `common/chat-peg-parser.cpp`). On the next request, `ChatMessage.promptText(format:)` must replay an assistant turn's prose `content` **and** its `tool_calls` (rendered via `ToolPrompt.toolEnvelope`) into the prompt — dropping the envelope when prose is present removes the only "prose + tool call" example from the history and trains the model to announce a tool and then stop without calling it.
- **Tool-call arguments must serialize JSON fragments**: `ToolPrompt.orderedArguments` renders each argument value with `JSONSerialization.data(withJSONObject:options:[.fragmentsAllowed])`. `.fragmentsAllowed` is load-bearing, not tidiness: without it a scalar argument (number/bool/null) is a JSON *fragment* and the call raises an **uncatchable ObjC exception** (`Invalid top-level type in JSON write`) instead of returning an error — `try?` cannot catch it, so it terminates the process (`_objc_terminate` → `ggml_uncaught_exception` → `abort`) on the serial inference queue. A model `read` call with `{"path":…,"limit":150,"offset":200}` aborted the server the moment pi replayed that turn (device crash 2026-10-18 11:58:53; the log's last line is the *request* that replayed it — `streaming #13 … async block started` — because the crash is in `formatPrompt` before any output). Every other `dataWithJSONObject` call site is safe by construction: `ToolCallParser.parse` guards with `isValidJSONObject` (which returns false for fragments) and the other two pass container roots — keep one of those two properties when adding a call site.
- **Tool streaming filters compose**: a tool turn runs each decoded piece through `ReasoningStreamFilter` **then** `ToolStreamFilter` (both in `ToolCallParser.swift`), so a `<think>` block emitted on a tool turn is stripped rather than streamed (it used to bypass the reasoning filter, leak the chain-of-thought as `content`, and — via `didStreamContentDuringToolGen` — suppress the cleaned content). `ToolStreamFilter` streams prose outside `<tool_call>…</tool_call>` and buffers the envelope; envelope tags are matched as whole literals (assumes the tokenizer emits `<tool_call>`/`</tool_call>` as single tokens).
- **`<think>` reasoning** blocks are stripped from streamed content by `ReasoningStreamFilter` (character-by-character state machine, NSRegularExpression for final parse).
- **`resolvedMaxTokens`** precedence: `n_predict` > `max_completion_tokens` > `max_tokens` for chat, `n_predict` > `max_tokens` for `/v1/completions`.
- **`enable_thinking`** can be top-level or nested under `chat_template_kwargs.enable_thinking`. Default is `false` (opt-in per request). The C API takes no template kwargs, so the flag reaches the prompt only through `ThinkingSwitch` (`Sources/App/ThinkingSwitch.swift`): thinking off appends the closed block the template's `enable_thinking is false` branch would have emitted (`<think>\n\n</think>\n\n` after the bare primer, or just the closer if a renderer already opened one), and any other prompt tail is left untouched. Without it the model reasons anyway — `ReasoningStreamFilter` still keeps that out of the client's `content`, but the tokens are spent and a short strict call can truncate (`finish=length`). `enable_thinking:true` returns the prompt unchanged.
- **OpenAI-spec field presence**: llm-comply's pinned spec marks `logprobs` (per choice), `refusal` and `content` (per message) required, and `model` required on input. The server encodes `logprobs`/`refusal`/`content` as **explicit null** when absent (present, never fabricated — see the `encode(to:)` override in `ChatMessage`/`ChatCompletionChoice`; Swift would omit a nil optional) and rejects a missing/empty `model` with a 400 via `ChatRequestSpec`. Do not remove these — the on-device `llm-compliance-test` skill (running `llm-comply openai-chat` against a deployed build) gates on them; regression shows as `chat-error-handling` failing (200 instead of 400) or content tests failing on missing fields (e.g. `chat-tool-calling` fails on a missing `content` when a tool-call turn drops it). The streaming path (`StreamingChoice`/`Delta`) needs no such fields and passes as-is.
- **Head dims come from GGUF `attention.key_length`/`value_length`** (suffix-matched via `LlamaInference.ggufMetaValue`), falling back to `n_embd/n_head`. Qwen3-4B stores 128 while derived is 80 — deriving alone under-counts f16 KV cost by 1.6× and the clamp approved unbackable contexts.
- **Hybrid models keep KV only on full-attention layers** (`KVCacheSpec.kvLayerCount`): the GGUF `<arch>.full_attention_interval` (e.g. Qwen3.5 SSM+attention, interval 4 → 8 of 32 layers) selects which layers cache K/V; recurrent layers have fixed-size state. Counting all layers over-estimates KV cost interval× (observed 36,864 vs actual 9,216 B/token → a viable 131,072 context clamped to 83,968).
- **The memory budget is the device's own measured ceiling — no assumed fraction of RAM may override it** (`MemoryBudget.ceiling` over readings of `os_proc_available_memory()` + `task_vm_info.phys_footprint`; the syscalls live in `ProcessMemory`, the policy stays pure). `os_proc_available_memory()` returns the limit *minus the caller's current footprint*, so the ceiling is their **sum** (capped at physical); `available == 0` is a *failed read*, not a zero ceiling. The **55%-of-physical floor was removed on 2026-10-18** because it silently overrode a *successful* measurement: the device logged `memory budget 6208012288B (6.21 GB) [limit 6442450944B (6.44 GB) = process-available 6350387288B + footprint 92063656B, physical 12263424000B]` — 6.21GB is 55% of physical minus headroom, a number no measurement produced, and the floor sat *above* the measured 6.44GB limit, so the measurement never got a vote. That is exactly why the line was unexplainable. Now the **largest successful reading of the launch wins**; half of physical applies only when *every* reading failed, and the line says `from fallback (every reading failed)` so an assumption is never read as a measurement. A low but *valid* reading is deliberately respected: a config that no longer fits is refused by the pre-check with its numbers logged, which is the intended trade. **A reading is taken more than once because the allowance can rise as the process settles** — and on this device it does not: three samples of 2026-10-18 (build `698dbbf`) each sum to **exactly 6,442,450,944B (6GiB)** — 6.35GB available + a 90.2MB footprint at init, 6.29GB + a 153.8MB footprint after the model load, 4.36GB + a 1.78GB footprint idle with both contexts live — i.e. **exactly the 6GiB tier the kernel bakes for this device**, and that is Apple's per-device constant rather than a fraction of RAM: xnu's `memorystatus_get_default_task_active_limit` takes `MAX(max_task_footprint_mb, memorystatus_entitled_max_task_footprint_mb)` and the second term is a **device-tree tunable** (`entitled_max_task_pmem`, `TUNABLE_DT_WRITEABLE`) — so the entitlement only *unlocks* the tier, and no SDK, build flag or app-side choice can exceed it (an independent report from the same model measures the same 6144MB *with* the entitlement, and xnu also shows the only knob above it, `increased-debugging-memory-limit` → the whole DRAM config, needs a profile sideloading cannot carry). The `~3.3GB un-entitled` figure these notes used to cite for contrast was a *class assumption* (`de71b9e`), never a reading on this device. The entitlement's own state is now logged at init (`MemoryLimitProbe`): `memory limit probe: base per-process limit N MB (kern.max_task_pmem), measured ceiling NB, increased-memory-limit entitlement present|ABSENT|unknown` — equal numbers mean the entitlement is decorative on that device, because the base tier already *is* the entitled tier. What was never real is the **~9GB class these notes used to claim**: it came from adding `available` to a 4.58GB reading `MemoryBudget` records as **rss**, and rss is not the ceiling operand. **What the ceiling does not cover**: the model's mmap (loading 2.78GB of weights moved the footprint by 63.6MB) and the Metal compute buffers (1.23GB of `sched_reserve` lines, private storage) are outside it, so a KV budget derived from it is a *bound on what to attempt*, not a measurement of the engine's total. So `LlamaInference.init` reads **twice** (`at init`, `after model load`), plans the KV clamp on the larger, and logs the budget line twice (the pre-load one exists so a refusal leaves the numbers on disk; the post-load one is authoritative). The file-size pre-check keeps the pre-load reading — it must run before memory is committed, so it is deliberately conservative. The budget line prints each reading's raw `available` + `footprint` + derived ceiling and names the winner, so the derivation is checkable from one line; the entitlement warning keys on the winning ceiling (below half of physical = missing uplift) or on the fallback having run. The heartbeat (`systemMemoryLog`) prints `footprint=` *and* `available=` in the same line, so `available + footprint` is the live ceiling check. **Every context counts, at its own size**: the MTP path creates a *second* context on the same model with the same `n_ctx` (`LlamaInference.setupDraftContext`) and llama.cpp commits its KV up front — so both the clamp and the fast-prefill slack charge `KVCacheSpec.chargedKvBytesPerToken` (target bytes/token **+ draft bytes/token**). The draft context is typed `LLAMA_CONTEXT_TYPE_MTP`, so llama.cpp builds only the model's nextn blocks (`llama_model_n_layer_nextn`, 1 on this model), and the device log of 2026-10-18 21:04 (build `698dbbf`) measures both at 80,128 tokens: target cache **1,330.25 MiB**, draft cache **166.28 MiB** — 2,176 B/token, exactly one of the target's eight layers. The earlier flat "two caches" count (`KVCacheSpec.kvCacheCount`) charged the draft 8× what it stores and clamped a viable **142,336** tokens down to **80,128**; charging one cache would over-approve just as badly, since the draft holds a real (if small) cache. The clamp's warning prints the split (`17408 target + 2176 draft x1 nextn`) so the number is checkable against llama.cpp's own `MTL0 KV buffer size` lines.
- **Which cap decided the context is classified, never guessed** (`KVCacheSpec.contextClamp` → `LlamaInference.contextClamp` → `ServerViewModel`). The UI used to print "Context reduced to \(N) tokens **to fit device memory**" for *any* reduction — including a hard ceiling the request tripped, while the KV cache was nowhere near its limit. The message now distinguishes a model-window cap from a memory cap (only the latter has a memory remedy), and `hardMaxContext` is 262,144 (the model's own window), so asking for the full window is no longer silently a hard-cap case.
- **Hybrid prefix reuse is a whole-state snapshot, not a `seq_rm` trim.** `can_shift=false` for SSM/hybrid caches, so `llama_memory_seq_rm` can never drop a suffix; `generate` instead restores the previous prompt's serialized sequence state (`restorePromptSnapshot` → `llama_state_seq_load_file`, saved by `savePromptSnapshot` → `llama_state_seq_save_file` into `NSTemporaryDirectory()`) and decodes only the suffix. This is *real* reuse — `KV snapshot restored (48337 tokens, prompt 48450); decoding 113 new` — and `ReuseSurvival` keeps it across a context recreate, so a recreate does **not** cost a full prompt re-decode. It is not free: the blob is ~664 MB at 32k tokens → ~897 MB at 48k (**~1.2 s and ~700 MB of writes per turn**, measured), and the next turn re-decodes the previous turn's generation (the snapshot is the *stable* prefix, taken before generation). The per-turn save is only needed because the MTP path ends by wiping `cachedTokenIds`/both caches (see the `usedMtp` branch at the end of `generate`) rather than leaving the live KV reusable — removing that wipe is the open optimisation in `docs/PERFORMANCE.md`.
- **Quantized KV cache** (`kvCacheType` q8_0/q4_0): only when `head_dim % 32 == 0` (llama.cpp b9553 validates per-head); quantized `type_v` requires flash attention, so `flash_attn_type` is forced `ENABLED` (AUTO can resolve off → constructor throw → NULL). Ineligible models fall back to f16 with a warn log (`KVCacheSpec.resolveCacheType`).
- **YaRN long-context** (`longContextYarn`): sets `rope_scaling_type=YARN`, `yarn_orig_ctx=32768`, and a factor **derived from the context being built** (`KVCacheSpec.yarnFactor(forContext:)` — the recipe's factor *is* the extension ratio: ×4 at 131,072, ×8 at 262,144, exactly the model card's documented 128K/256K recipes; a fixed ×4 left everything past 131,072 unscaled) on every context (target/MTP/recreate). It lifts the `n_ctx_train` clamp; llama.cpp then re-sets `n_ctx_train = yarn_orig_ctx / rope_freq_scale` (`llama-context.cpp`, only when the freq scale differs from the model's trained one), so the derived factor lands the adjusted window exactly on the built context. Still memory-clamped, and `hardMaxContext` (262,144) is the outer bound.

- **Log split + panel budget**: `FileLogger` routes each line to one of three files by `LogRouter.category(level:sourceFile:)` — `.verbose` always goes to `llamaserver-payloads.log`, `LlamaInference.swift` to `llamaserver-inference.log`, everything else to `llamaserver.log`. The in-app panel renders **basic (error/warn/info) lines only** (`LogPanelSpec`), truncated to 500 chars, in a `LazyVStack`. Do not route payload/debug lines back to the panel or raise the cap without checking the cost: a `cpu_resource` report (bug_type 202, 57% CPU) traced the app's heaviest stack to the panel laying out 72k-char prompt lines with `.textSelection(.enabled)` at 10 Hz.
- **Logs come off the device over HTTP**: `GET /logs` (also `/v1/logs`) returns the three files so a LAN client can pull them without the Files app — `curl 'http://<device>:8443/logs?name=inference&tail=500'`, `?backups=0`, `?format=json`. The contract is the pure `LogFetchSpec`; `FileLogger.snapshot(_:)` flushes buffered lines first, then reads backup+live per category. It returns whatever the files hold, so with "log prompt & response content" on it exposes prompts and completions (the payload file) to anyone on the LAN; that toggle is off by default. Each fetch logs one `GET /logs …` line to the server file.

## Style conventions

- `OSAllocatedUnfairLock` for thread-safe flags/counters (not `os_unfair_lock` C API).
- No `#warning` — use `FileLogger.shared.warn(...)` for recoverable issues; the log is crash-survivable.
- FileLogger: error/warn are written AND fsynced synchronously (crash breadcrumbs survive aborts); info/debug/verbose are buffered on the logger queue (fsync ≤ 1s / 64KB) so the inference path never blocks on I/O; NSLog fires for warn+ only; the on-screen mirror delivers ≤ 10Hz batches and carries **basic (error/warn/info) lines only**. Set `minimumLevel` from UI `.verbose` to capture full request/response payloads.
- FileLogger writes one file per `LogCategory`: `llamaserver.log` (server/HTTP lifecycle), `llamaserver-inference.log` (engine internals), `llamaserver-payloads.log` (the `.verbose` payload dumps). Routing is `LogRouter.category(level:sourceFile:)`; the `file: String = #file` default on every log method supplies the source, so call sites need no category argument. Each file rotates at 1 MB to `<name>.1.log`.
- `llama_log_set` routes llama.cpp native logs into FileLogger at `.debug` level.
